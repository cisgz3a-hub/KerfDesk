## ADR-653 - Preserve program, document and remote-edit meaning across audited boundaries

**Status:** Accepted for implementation by the maintainer's 2026-10-21 instruction to fix the code audit findings, audit again and open a PR. This amends ADR-630's Marlin interpretation and ADR-498's scaled gap layout. It adds no machine, licence or publication permission.

## Context

The current-source audit reproduced eight gaps: external Marlin programs were interpreted as GRBL blocks; project labels could escape generated G-code comments; small whole-number S ranges rounded useful power to zero or full power; ordinary insertion could exceed the project loader's limits; clipboard text lost its embedded fonts across documents; Copy Along Path ignored changing copy sizes when computing gaps; large valid workspace summaries exceeded the MCP result limit; and remote width placement silently ignored horizontal lines.

## Decision

1. **Review the connected controller's executable semantics.** External Marlin runs send `G21` and `G90` on separate lines. Normalization preserves whitespace that matters to Marlin numbers. Inspection and warning scans share a Marlin interpretation of the first command and its own parameters; trailing G/M words do not become extra commands. The original normalized executable is still what Start sends. Serial line-number/checksum framing is refused because this sender does not implement Marlin's resend protocol. Build-dependent motion and coordinate changes are disclosed and excluded from the known Frame outline, including dependent relative coordinates, under ADR-630's existing known-placement rule. CNC and laser tool behavior are distinguished. The parser identity travels with the reviewed program and its Frame evidence.
2. **Keep metadata inert and power versioned.** Reuse the audited comment-label repair and ADR-567 Amendment 1's power-scale version 3. Labels become single inert comment values. Small GRBL-family S ranges retain fractional power; archived versions 1 and 2 reproduce their own bytes. Reported empty firmware power ranges remain review warnings.
3. **Validate complete insertions before publishing state.** Drawing, text, vector/image import, trace insertion, manual operations and operation cloning obey the same scene budgets as persistence. A refusal preserves the project, selection and Undo/Redo. Text and editable-relief creation keep their drafts and remain retryable, imports report failure and remote commands do not acknowledge artwork that was never inserted. The existing font-count persistence limit applies to imported text and Paste as well.
4. **Carry clipboard font dependencies.** Copy includes only embedded fonts referenced by copied text. Paste reuses identical bytes, remaps conflicting keys, preserves destination text, and does not silently substitute a destination font for missing source bytes. Font loading validates the current document's bytes before cache reuse, and CSS font registration prevents an older asynchronous load from replacing the current resource. The copied project remains editable after Save, reopen and a fresh font-loader session.
5. **Space scaled copies using their final extents.** Gap layout uses both neighboring copies' sizes, including the closing seam. Count and Apply share the same layout; changing the available project capacity cannot silently change the chosen layout. Straight or rotating layouts use the arithmetic-series count. Upright copies on bends use a deterministic feasible-count search and can leave spare room; discontinuous tangent extents do not support a monotone maximum-packing claim. Trial layouts use arithmetic runs per guide segment rather than allocating every candidate copy. Count/centre-spacing modes retain their existing meaning.
6. **Budget the final workspace response.** Renderer and MCP boundaries account for UTF-8 and MCP's structured plus text representations. Oversized summary lists retain complete ordered prefixes, original totals and explicit truncation. Selection identity stays independent; a client cannot calculate selection bounds from an incomplete set of artwork summaries. Other oversized results retain the existing failure guard.
7. **Apply representable remote width requests atomically.** Uniform width placement works for horizontal artwork while keeping its zero height. A zero-width object cannot acquire a positive width by uniform scaling and reports that limitation without committing an insertion. Imported image resources are accepted only when the enclosing edit or batch succeeds; failed edits release their staged resources.

## Verification and boundaries

Regression tests exercise independent firmware-model comparisons, exact transmitted bytes, malformed comment labels, fractional power and archive versions, real store insertion plus persistence, fresh-session font loading, scaled geometry, official MCP client/server transport, and remote transaction/resource rollback. A second review checks interactions between these fixes. Test results belong to the PR's current source and checks; software evidence does not establish controller, air-cut, material, packaged-installation or physical-machine qualification. Frame remains the sole ordinary Start policy gate. This task neither merges nor releases the result.

Marlin behavior was checked against its primary sources: [parser](https://github.com/MarlinFirmware/Marlin/blob/2.1.2.8/Marlin/src/gcode/parser.cpp), [command dispatch and destinations](https://github.com/MarlinFirmware/Marlin/blob/2.1.2.8/Marlin/src/gcode/gcode.cpp), [cutter commands](https://github.com/MarlinFirmware/Marlin/blob/2.1.2.8/Marlin/src/gcode/control/M3-M5.cpp), and [serial queue](https://github.com/MarlinFirmware/Marlin/blob/2.1.2.8/Marlin/src/gcode/queue.cpp). The interpretation is independently implemented; no upstream implementation is incorporated.

## Amendment 1 - Disclose build-dependent inline power after M5 (2026-10-22)

In inline mode, `M5` without `I` disables Marlin's inline output, and a later `M3`/`M4` without `I` sets power without re-enabling it (`M3_M4` calls `set_enabled(true)` only in its `I` branch). With the default `Configuration_adv.h` the following moves stay dark, which is what the review shows and what the independent firmware model in `src/__fixtures__/controllers/marlin-laser-power-model.ts` reproduces. With `LASER_POWER_SYNC` enabled, `M3` queues a power-sync block whose power the stepper applies directly (`stepper.cpp`), and the disabled moves that follow leave that output unchanged, so unless the board also drives a separate laser-enable pin (which `M5` switched off) the laser fires until the next `M5`. The preview cannot tell which build is connected, so this sequence now adds a review warning naming both outcomes. It remains a warning under ADR-565; the default-build interpretation and the streamed bytes are unchanged.
