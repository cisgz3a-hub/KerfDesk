## ADR-561 Amendment 6 - Retain discoverable manual installer history

Date: 2026-10-11

Status: Accepted for implementation by the maintainer's request to fix the payment audit findings. Publication evidence remains separate.

### Context

A paid licence keeps Pro access to releases covered by its update year. The download page exposed older code-signed releases, but the current manual Windows lane exposed only `latest.json`. Once the latest release exceeded that year, the customer had no list from which to find a covered installer. This resolves the website limitation recorded in ADR-561 decision 5.

### Decision

1. Publish `desktop/commercial-manual/catalog.json` containing the original, independently stable-key-signed per-version download manifests. Each browser record must pass the existing manual manifest signature, product, stable channel, version, source, date, artifact name, size and hash checks. The catalogue cannot supply download URLs. The existing download host and versioned paths are computed from verified fields. The original manual manifest schema and installed updater remain unchanged.
2. Show verified earlier installers on `/download.html`, with release dates and SHA-256 hashes. Preserve manual releases when the code-signed lane starts, preferring the signed copy of a version present in both lanes. `?version=1.0.14` selects that exact stable release. An unavailable or unverifiable requested version never silently selects latest. Preview version selection keeps its existing meaning.
3. The first manual publication with an existing latest requires reviewed migration evidence pinned to that exact latest SHA-256. A bounded, complete R2 object listing identifies the archive to review; it is not evidence that an uploaded version was promoted. The evidence file explicitly classifies every immutable manifest at or below latest as published or abandoned, pins its bytes by SHA-256, and references the operator-reviewed publication or interruption receipt. Only confirmed published entries enter history. Each still passes manifest signature and version-path verification and requires its corresponding installer object. Missing, stale or incomplete evidence refuses publication before writes; it never silently drops a legitimate earlier release or guesses that a lower version was published. Versions beyond authenticated latest remain excluded. Later normal publications preserve every historical record. A 128-release or 512-KiB limit refuses publication until reviewed pagination is added; it never prunes customers' covered versions.
4. Verify the candidate installer and immutable objects first. Recheck the reviewed latest and initial history, write and read back history, then recheck and promote latest. Browsers cap the index at authenticated latest, so an interrupted history-first write cannot offer a future candidate. When preparing a later publication, remove entries above the authenticated previous latest except an identical current-candidate retry. Without a previous latest, retain only the current candidate. This prevents an abandoned history-first upload from becoming advertised history after another version is promoted; its immutable objects remain intact. Identical retries converge, and a catalogue ahead of the current candidate still refuses publication. Existing shared workflow serialization is required; these read/compare/write checks are not a storage-level compare-and-swap against uncoordinated administrator writes.
5. Existing deployments without a catalogue still offer verified latest. Only when history is missing, corrupt or incomplete can exact older-version links verify the immutable manual manifest directly, with its version capped at authenticated latest. A healthy catalogue controls which versions are offered. A catalogue missing its authenticated latest entry is incomplete: retain its verified entries, add independently verified latest, and display support guidance. It never falls back from an invalid code-signed catalogue to an unsigned release.
6. Catalogue membership is owned by the serialized publisher and trusted storage administrators. Its original per-release signatures authenticate the installers, not catalogue completeness. A valid out-of-band replacement that removes older entries while retaining latest cannot be detected from the remaining catalogue and current latest alone. Scanning all immutable uploads cannot repair that state safely because the same archive can contain abandoned candidates. The browser's incomplete-history warning covers detectable missing or invalid history, not arbitrary valid subset replacement. Recovery of such a replacement requires reviewed publication receipts; no signed-completeness or append-only promotion protocol is claimed here.

### Rollout and verification

Deploying the website enables history reading and exact-version selection. Before the next authorised manual Windows publication can backfill a legacy archive, review and commit `docs/releases/manual-download-history.json` using the receipt requirements and schema in `scripts/manual-commercial-release-README.md`. The workflow passes this one evidence file if present; an absent required file fails with recovery guidance. A local authorised operator can provide the same file using `--reviewed-history <file>`. Once a verified catalogue exists the migration evidence is no longer used; a later missing catalogue requires fresh evidence pinned to its current latest. An identical previously published candidate can also create a missing catalogue with reviewed evidence, subject to existing operator and package qualifications. Merging source neither supplies evidence for live releases nor populates the live archive. No new unattended release or provider mutation is introduced.

Focused tests cover original signature and download checks, numerical version ordering, mixed signed/manual history, exact-version success and refusal, absent and corrupt history, interrupted publication, concurrent mutable-state changes, historical backfill, immutable path conflicts, missing historical installers, complete bounded listing, and refusal to prune a full history. Native installation and live publication still need their own evidence.

R2 listing follows the [Cloudflare object-list API](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/subresources/objects/methods/list/), including `prefix`, `cursor`, `per_page` and `result_info.is_truncated`.
