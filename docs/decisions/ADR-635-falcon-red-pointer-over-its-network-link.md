## ADR-635 - The Falcon A1 Pro's red pointer is switched over its network link

**Status:** Superseded by ADR-664 on 2026-10-22: on the maintainer's machine assist light 0 lit the wrong light, and the A1 Pro's LED is now its laser at low power. Accepted by the maintainer on 2026-10-19 ("The LED doesn't work … In the Creality Falcon's own software they just have a button to switch LED on, not different things to go fill in"; asked which light, they chose the red pointer on the head). Amends ADR-603 and ADR-605. Software verification only; the pointer has not yet been switched on a machine by KerfDesk.

**Context.** Machine Setup → Positioning LED / crosshair accepts only one documented accessory M-code for on and one for off (ADR-603, ADR-612). The Falcon A1 Pro has no such command: Creality's LightBurn bundle has no light macro (`docs/audits/2026-09-19-machine-compatibility-fixes/falcon-vendor-configuration.json`), and no public G-code for it was found. On an A1 Pro the section could only be filled with guesses, so the operator got "Positioning light on command must be one documented accessory M-code …" and no light.

Creality's own Falcon Design Space switches the machine's lights through the A1 Pro's embedded HTTP server, the one that serves its camera at `http://<machine>:8080/media/getCapturePhoto` (ADR-116). Static analysis of the installed Falcon Design Space 1.9.2 (`FalconDesignSpace.exe`, SHA-256 `008dc04b95254436f214a640c80e97a293001f1f672cb20d885950d35f55ee20`; strings, the Qt resource QML and the x64 code that builds each request) found:

- `DeviceController::setAssistLight(index, isOpen)` → `HttpDeviceDriver` → `POST /device/assistLight`, `Content-Type: application/json`, body `{"switch": n}` where n is `isOpen` as an integer (index 0 uses the key `switch`; other indexes use `switch<index>`).
- `setLightBar(dutyCycle)` → `POST /device/setLight` `{"dutyCycle": n}` (the light strip), and `setAssistLaserAssistled(isOpen)` → `POST /work/laserAssistled` `{"switch": n}` (used only for the Falcon T1).
- Setters go through the JSON `post` helper; getters (`/system/getDeviceModel` and the like) through `get`.
- Camera calibration switches assist light 0 off for every model while it photographs the bed and back on afterwards, which identifies it as the visible pointer on the head. That identification is inferred from Creality's code, not measured.

No decompiled code or Creality asset is copied into KerfDesk; only the request shape is reproduced.

**Decision.**

- `PositioningLight` becomes a union. The existing G-code mapping is unchanged. A new `{ kind: 'creality-falcon-pointer', offsetXmm, offsetYmm, afterFrame? }` carries no commands. It is valid only on the `creality-falcon-a1-pro` command set (`devicePositioningLightIssue`), which Machine Setup and saved-profile recovery enforce; project files keep it structurally.
- On the Falcon A1 Pro profile, Machine Setup → Positioning LED / crosshair shows one checkbox, **Use the Falcon's red pointer**, with the pointer offsets (default 0) and **Centre & LED after Frame**. There are no command fields. The Falcon-compatible GRBL profile says to choose the A1 Pro profile for this.
- **LED on**, **LED off**, **Artwork centre & LED** and Centre & LED after Frame keep their owned controller transaction (ADR-603, ADR-605): Idle check, beam-off `M5`, fence, beam-off move and position check. Only the light step changes. Instead of a G-code line, it asks the desktop camera bridge's new `POST /falcon/pointer?host=<ip>&state=on|off`. The bridge sends exactly `POST http://<ip>:8080/device/assistLight` with `{"switch":1}` or `{"switch":0}`. The bridge accepts only a bare private-network IPv4 address in plain decimal (never loopback, a name, a port, a path, or an octet with a leading zero, which the URL parser reads as octal: `010.8.8.8` is 8.8.8.8), the usual trusted Origin and Host, and POST only. It refuses redirects, waits 5 s, and queues behind any camera frame to the same machine, because the embedded server wedges under concurrent requests (ADR-116). An HTTP error is a failure. A 2xx reply whose body is a JSON object with a numeric non-zero `code` is also a failure; any other 2xx reply, empty or not JSON, is accepted, because the request's evidence says nothing more about the reply.
- The machine's address comes from the Falcon camera KerfDesk already reaches: a discovered or active `http://<ip>:8080/media/getCapturePhoto` URL (never a phone or other snapshot camera). Failing that, it uses the bridge's existing camera discovery, which only accepts a host that served a JPEG at that path. Discovery runs before the LED transaction takes the controller, since it sends the controller nothing and can take seconds; the request is then admitted again. A discovered address is reused until a switch cannot reach it, the controller connection changes or another machine profile is chosen. The light's own on and off requests stay inside the owned transaction, including the off before a move: the pointer can be lit outside KerfDesk (Creality's software, a restart), and the recorded state is command tracking, not the light's actual state.
- If the request never left KerfDesk (web app, no bridge, Falcon not found), the light stays recorded as off. A request that may have reached the machine (an HTTP error or timeout after sending) keeps **LED off** available, like an unacknowledged G-code light. Disconnect sends the pointer off over the network, best effort, without waiting.

This adds no Start guard, no policy refusal and no new licence check. It never sends G-code for the pointer, so no command can reach the cutting laser through it.

**Consequences.** The A1 Pro gets a working LED with one tick and no commands, but only in KerfDesk Desktop and only when the PC can reach the Falcon's network link (as Falcon Design Space and the camera require). The light strip (`/device/setLight`) is not exposed; it can be added the same way if wanted.

**Verification.** Unit tests cover the exact request (method, path, content type and body) against a loopback mock Falcon, the bridge's refusals (public, loopback or leading-zero host, bad state, GET, untrusted Origin), a non-zero reply code, the client's POST, validation and normalization of the new light and its command-set rule, the editor's one-tick setup, and the LED transaction: beam-off first, the pointer only after the move, the camera's address preferred over discovery, discovery before the controller is held and again after a disconnect or profile change, never a phone camera, and the on/off state after unsent and uncertain requests. Hardware qualification on an A1 Pro remains open.
