## ADR-568 - Bounded artwork sharing, authoring and job review through MCP

**Status:** Accepted for the workspace expansion requested by the maintainer on 2026-10-04. Extends ADR-564. Hosted, native, customer-release and physical-machine evidence remain separate.

**Context.** The maintainer requested the recommended first phase of MCP expansion: useful current job review, artwork previews, bundled font and existing-text controls, layout controls and Undo/Redo. The original integration excluded source artwork and independent copies. This extension must explicitly define those boundaries instead of silently expanding the data shared by existing approvals.

**Decision.** Existing read/edit pairing, OAuth scopes and the live sandboxed renderer authority remain in force. A separate desktop preference, initially off, enables **Share artwork previews and text with approved phones and MCP apps**. Enabling remote access or granting viewing/editing does not enable artwork sharing. The desktop explains that approved phones and MCP apps, including an app's AI provider, can receive this content. Disabling sharing during an asynchronous read prevents the result from returning pixels or text.

The portable server adds `get_workspace_preview`, `list_fonts`, `get_text`, `update_text`, `arrange_artwork`, `undo` and `redo`; `add_text` gains an optional bundled `fontId`. Ordinary summaries retain bounded IDs, bounds, operation parameters, selection and current history/permission hints. When artwork sharing is off, operation labels are generic because automatically named text operations can retain the original wording after conversion to paths. Job-review warnings retain their substantive meaning but remove artwork-derived wording. Returned content is untrusted data, never client instructions.

Previews render supported visible artwork using actual desktop geometry. They exclude cameras, external URLs, file reads and complete project files. A PNG is at most 1024 pixels on either axis and 65536 base64 characters; its header must agree with its declared dimensions. Unsupported or oversized scenes report unavailable without silently omitting contributing artwork. Standard MCP clients receive an image content block. MCP Apps hosts can load the static `ui://kerfdesk/workspace/v1.html` resource with `text/html;profile=mcp-app`, an empty external-network/resource allowlist and host-mediated tool calls. The self-contained panel works without a model API key. The phone control page remains separate from the public mobile product page and does not mount the desktop machining canvas.

Text controls expose only the bundled font catalog. Ordinary text edits use the existing geometry, dirty-state, history and autosave actions, preserving transforms, operation associations, bend and weld settings. Path text and variable text editing are outside this phase. Layout supports alignment, centre distribution, mirroring, grouping, ungrouping, duplication and deletion. Entire target groups and copy/deletion dependencies are validated before editing; locked, hidden, missing or unsupported targets refuse the complete request. Creating an independent Pro copy uses ADR-540's existing admission rule and returns `needs_pro` without a deferred remote action or licence prompt. Existing artwork edits and Undo/Redo retain their ordinary contract.

All writes require the latest revision and caller UUID. Identical uncertain retries retain that UUID; conflicting arguments, local edits, New/Open, permission loss, cancellation and session replacement cannot publish an old asynchronous edit. The shared portable mutation classification drives relay, native permission checks and tool metadata, preventing new writes from acquiring read-only access by omission. UI permission hints grant no authority.

`review_job` reuses an exact current desktop review or compiles the current job through canonical read-only preparation. It does not open or approve a dialog, query a controller, Frame, Start or dispatch executable output. Its owner fences document, output scope, placement, machine/camera observations and cancellation. Readiness describes successful current compilation; a completed Frame is independent spatial evidence under ADR-565, never an invented physical qualification. Preview bounds use artwork coordinates, while review bounds use the prepared program's output coordinates.

**Consequences.** Paired clients gain useful workspace controls while the computer must remain awake, online and running the updated app. Remote execution, recipes/layer creation, file exchange, saved workflows and live machine control remain separate future work. This adds no account, licence, Frame or Start gate. Existing Pro admission and the sole ordinary completed-Frame Start policy are unchanged. Local protocol/browser checks, a hosted Worker, actual ChatGPT rendering, an installed desktop update and hardware qualification require their own evidence. The desktop release cadence is governed by [ADR-561 Amendment 4](ADR-561-amendment-4-ten-pr-release-batches.md), including its explicit early-release override.

The maintainer also requested an easy, comfortable interface. Paired phones open directly to the workspace, existing text editing is a primary task, and less common controls use expandable sections. Touch targets, readable inputs, bounded font scrolling and selection feedback must remain usable on small phones. Desktop setup presents a clear readiness state, a readable pairing code and copy actions; MCP server details stay in a separate disclosure. These presentation choices do not grant permissions or change request admission.
