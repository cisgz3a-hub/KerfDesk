## Findings

### T14-P2-1: OK on one photo silently changes how every other photo on the same operation burns, and the dialog does not say which fields are shared
- **Severity P2:** a missing warning that changes another object's burn. If a user ticks Negative Image (or changes dither, Min Power, DPI, Dot Width or Pass-through) for photo B, photo A, elsewhere on the bed, also changes. All of A's pixels are inverted, and nothing is said about A. It is not P1: the job Preview shows A's new burn, and the shared semantics are intended (LightBurn parity, ADR-581 Context, register row 21 "Shared-layer behaviour is retained"). The defect is the disclosure. LightBurn's dialog groups these controls as "Layer Settings", and its docs say "Changes affect any image on the same layer". KerfDesk's dialog has no grouping, heading or note (`AdjustImageDialog.fields.tsx:31-89`, `93-206`). Its header names only the file (`AdjustImageDialog.tsx:253-266`). The design canvas does not show A's change either: it shows image tones only, "not an operation's Invert brightness" (`raster-adjusted-display.ts:10-11`). A refuter could argue for P3 on LightBurn parity, since the job Preview does show it.
- **Where:** `src/ui/state/raster-adjustment-actions.ts:44-58` (no override → `updateLayer(scene, operation.id, operation.patch)`); `src/ui/raster/AdjustImageDialog.fields.tsx:31-89` (one flat grid mixing image and operation fields).
- **Repro (ran):** `C:\Users\stolk\kd-t1\zz-t14\t14b.test.ts`, log `t14b.log`. Run from the tree: `NODE_OPTIONS=--no-experimental-webstorage node node_modules/vitest/vitest.mjs run --config ../zz-t14/vitest.config.mts --maxWorkers=1 t14b.test.ts`. Two identical 32×8 photos A (x 10) and B (x 60) are on one Grayscale operation, and neither has an override. Open Adjust Image on B, tick Negative Image, set Brightness 10, OK. **Photo A: 256/256 burned pixels change (total S 101,236 → 103,564), layer `negativeImage: true`.** Expected from the dialog's wording: A unchanged.
- **Oracle:** LightBurn Adjust Image reference (Layer vs Image settings groups and the "any image on the same layer" sentence). Also the owned-override path of the same action, which leaves B untouched (C2: 0 px differ).
- **Suggested fix:** split the grid into "Image" (Brightness/Contrast/Gamma) and "Operation <name>" groups. When other objects use the operation and the image owns no override, say "Also changes N other images on <operation>", or offer "Only this image", which writes an image override as Photo engraving does.

### T14-P3-1: OK with nothing changed still records an Undo step and marks the project modified
- **Severity P3:** tidiness, with no burn change. C6: open Adjust Image on an image without stored tones, press OK. The image gains `brightness: 0, contrast: 0, gamma: 1`, the Undo stack grows by 1 and `dirty` is true. One Undo then appears to do nothing.
- **Where:** `src/ui/state/raster-adjustment-actions.ts:40-62` (`changed` is true whenever the image is found, not when a value differs); `AdjustImageDialog.tsx:235-251`.
- **Repro:** `zz-t14\t14a.test.ts` C6 (`t14a.log`: "OK unchanged on B: project identical false; undo 1; dirty true").
- **Suggested fix:** in the action, return `s` when the normalized image patch and the operation patch equal the current effective values.

## Not a defect / limits
- **Preview dithers a ≤ 420 px thumbnail, unoriented, without mask, sharpen or tone calibration:** KNOWN rolling v2 20-K-5 / Q3-K4 (also 20-K-1, Q1-P3-K4 "compile orients then dithers"). ADR-581 Context and ADR-670 record it. B quantifies it at 1:1: identical tone for Grayscale/Threshold, dot positions differ for diffusion/Ordered, mean darkness within 0.02. ADR-028 Amd 1 governs the compiled preview, not this thumbnail.
- **Non-finite tones from a preset file resolve to the darkest setting** (`form-utils.ts:3-5` `numberValue` falls back to `min`; `raster-adjustment-actions.ts:92-94` `clamp` → `min`; `user-presets.ts:218-228` `typeof === 'number'` admits `1e999`): KNOWN rolling v2 20-P3-1, still open (re-read; typed fields are safe per D). The core LUT side was fixed by O6-P3-3 (#1787).
- **Gamma direction opposite to LightBurn:** KNOWN O6-P2-1, kept by ADR-671 Amd 1. The dialog states it.
- **Transparency:** a `RasterImage` stores only the over-white luma, so Adjust Image cannot tell a transparent surround from white paper. A white logo on a transparent PNG imports blank, and Negative then burns the whole rectangle. That is the import model (ADR-349/ADR-685), not this tool. ADR-404 decision 5 handles polarity for Trace only.
- **Min Power is ignored by dithered modes:** by design (LightBurn: min power applies to grayscale shading); the tooltip says so.
- **Density shown at the compiler floor** (0.5 l/mm stored shows 1 mm / 25.4 dpi) is what burns (`raster-units.ts:14-24`).
- **Not checked:** no browser run (brief: memory, no browser). So keyboard, focus, Enter-to-OK with a pending draft, the real canvas drawing, and browser latency were not exercised. Pass-through, masks, rotated/mirrored images and preset Import/Export were not re-run (register row 21 and rolling v2 covered them). Blue-noise was compared for preview vs burn only, not against an independent oracle.
