# KerfDesk speed and worker bottleneck audit — 14 October 2026

The strongest confirmed targets are whole-project structured cloning on the UI thread, interactive work waiting behind background preparation, duplicate ETA/Preview compilation, and sequential-scan eviction in the artwork sprite cache. Adding more workers alone would not resolve these costs.

Audited source: `03f1da57737ebc58d7cf4e240be6c2225270c690`, the fetched `origin/main` at audit start. Local branch: `codex/performance-audit-20261014`. Application source is unchanged; this branch adds audit probes and evidence. No hardware, deployment, or provider state was exercised.

Environment: Windows 11 Home, Intel i9-13900H, 20 logical processors, approximately 31.6 GiB RAM, Node 24.15.0, pnpm 11.3.0, Chrome 155.0.8059.40. Other user applications stayed open. Audit workloads ran serially. Small timing differences should not be treated as universal constants.

## Prioritised findings

### 1. Whole-project worker requests can block the UI for hundreds of milliseconds

`src/ui/laser/output-preparation-worker-client.ts:233` sends the complete output envelope with ordinary `postMessage`; `src/ui/workspace/design-scene-worker-client.ts:109` does the same for design scenes. Their projects include object-heavy vector geometry. The existing packed transfer protocol is already used for Preview/ETA and other clients, but these paths do not use it.

A native Chrome Worker echo probe compared the same immutable project containing a polyline plus its canonical straight-line curve. Three samples followed warmup; fixture creation, worker startup and validation were outside timing.

| Points | Raw synchronous post, median | First packing | Cached packing, median | Packed synchronous post, median |
| ---: | ---: | ---: | ---: | ---: |
| 50,000 | 13.7 ms | 3.2 ms | 0.3 ms | <0.1 ms |
| 200,000 | 62.6 ms | 8.3 ms | 0.7 ms | 0.1 ms |
| 1,000,000 | 595.7 ms | 44.8 ms | 3.5 ms | 0.1 ms |

The million-point raw post ranged from 491.6 to 679.9 ms. This isolates boundary cost, not actual compilation or complete Start/Save latency. Packed receiver reconstruction is excluded. Echo roundtrip figures include two crossings and must not be substituted for a production request's cost. Sub-0.1 ms results reflect timer resolution, not zero work.

**Next change:** extend the existing exact packed-project protocol to output and design requests; preserve snapshot ownership, all non-vector data, and exact generated bytes. Measure cold packing, receiver unpacking and final UI commit separately. The evidence does not justify weakening any output or Frame contract.

### 2. Interactive Save and trace-part editing can wait behind an unrelated long preparation

`src/ui/worker-memory-lane.ts:16` is one non-preemptive FIFO. Preview/ETA reserves it at `preparation-worker-client.ts:403`; manual project Save at `project-save-preparation-client.ts:44`; trace-part preparation at `trace-part-worker-client.ts:47`. The lane is a deliberate memory protection, but it has no interactive priority or preemption. Closing Preview only cancels delivery/scheduled launch in `use-preview-toolpath.ts:105–108`; already-dispatched work remains active.

Four deterministic audit tests passed using production clients and the real scheduler with controlled Worker replies and fake time. Manual Save remained queued throughout a simulated two-minute preparation and started only when that preparation finished. Trace-part preparation similarly remained queued beyond its own execution timeout. **These are scheduling reproductions, not observed two-minute wall-clock waits.**

**Next change:** expose queue versus compute time, cancel work when it has no remaining consumer, and prioritise interactive requests while retaining the memory budget. Do not remove the lane or blindly raise concurrency.

### 3. An active ETA cannot be promoted to Preview, causing duplicate compilation

`preparation-worker-client.ts:147` reuses a cached Preview, while promotion at `:189` only examines queued requests. If an estimate has already dispatched, Preview waits and then sends another preparation. Both worker paths compile the job (`preparation-worker.ts:134,153`). The audit reproduced two dispatches for identical project/options; the reverse order, Preview followed by ETA, correctly shared one dispatch.

**Next change:** make active result demand upgradeable or retain a reusable compiled intermediate with an explicit memory limit. Keep the useful estimate-only policy that avoids constructing an unused large preview route.

### 4. The artwork sprite cache can lose all reuse with nine visible dense objects

`artwork-sprite-cache.ts:36` caps the cache at eight entries. Eviction at `:347–356` removes the least recently used entry, while `draw-scene.ts:313` visits objects in stable order. A working set just larger than the cache cycles through misses on every redraw.

The real Canvas2D probe used small sprites, safely below the pixel budget, with independent keys and three stable passes:

| Dense object keys | Paint calls, pass 1 | Pass 2 | Pass 3 |
| ---: | ---: | ---: | ---: |
| 8 | 8 | 0 | 0 |
| 9 | 9 | 9 | 9 |
| 16 | 16 | 16 | 16 |

This reproduces unnecessary repaint work reliably; it does not measure full-app GPU frame time. The tiny fixture's repeated nine-object passes took about 1.6–1.7 ms, so a large real-artwork pan/zoom benchmark is still needed to quantify user impact. Objects enter this cache at 4,000 display segments. Pixel-budget pressure can create the same pattern with fewer objects.

**Next change:** use admission/retention that resists sequential scans, bounded by pixels and memory. Simply increasing eight to a larger count only moves the cliff.

### 5. Quantity nesting validation scales quadratically and also runs during Accept

`src/core/nesting/outline-compact-nest.ts:254–260` checks rectangle pairs and creates suffix arrays. At 10,000 placements it can inspect 49,995,000 pairs. Accept materialises synchronously through `use-production-nest-review.ts:60`; sheet materialisation validates, clones, and serializes/deserializes each sheet (`production-nest-sheet-materialize.ts:33,58–59`). Preparation also stringifies artwork to estimate its size (`prepare-production-nest.ts:66–71`).

| Non-overlapping placements | Validator median | Range, three samples |
| ---: | ---: | ---: |
| 1,000 | 5.7 ms | 5.2–5.8 ms |
| 5,000 | 61.8 ms | 60.8–103.6 ms |
| 10,000 | 243.2 ms | 234.2–259.9 ms |

These are isolated Node production-validator timings, not measured browser Accept latency. All layouts validated successfully. The existing six-part nesting benchmark times the planner and excludes Prepare/Accept.

**Next change:** use a spatial broad phase before the exact overlap predicate, remove suffix-array allocation, and measure Prepare, Plan and Accept independently. Preserve final placement validation.

### 6. Startup is quick locally, but its script payload exceeds the product budget

A fresh production web build loaded its welcome/workspace surface in a median **1,169 ms** (1,131–1,196 ms, three fresh Chrome contexts). The local server used precompressed gzip assets, and no page errors occurred. This is local startup execution and transfer, not WAN performance or installed-desktop startup. Service workers and external requests were blocked; first-install precaching was excluded.

The startup journey requested **1,933,805 compressed JavaScript bytes**, before counting styles/images, already above `PROJECT.md`'s 1 MB compressed bundle target. All measured subresources totalled 2,094,078 compressed bytes. Four scripts account for 94.6% of the JavaScript payload:

| Chunk | Gzip bytes |
| --- | ---: |
| ui-workbench | 735,226 |
| core | 481,878 |
| main | 394,234 |
| io | 217,349 |

The build also generated a 410-entry, 32,201.88 KiB precache manifest. That is the build's uncompressed offline inventory, not measured first-load network transfer. `vite.config.ts:248–252` groups broad core, I/O and workbench modules. **Next change:** inspect startup code coverage and dependency edges, then split genuinely optional feature entry points. Do not claim an arbitrary chunk can be removed without checking its consumers.

Lab-only FCP ranged from 77–314 ms; observed LCP from 314–1,216 ms; CLS was approximately 0.00011. These short scripted sessions are not field Core Web Vitals, and LCP stops at the scripted welcome click. No field INP was collected. The longest pre-welcome tasks were 135–170 ms. Bundle hashes, resource timings, screenshot, accessibility snapshot and a separate fourth CPU-profiled trial are retained.

## Measurements that limit the conclusions

The initial existing browser bundle of nine cases produced eight passes and one failure. The heavy G-code canvas case exceeded its 1,000 ms heartbeat-gap budget at 1,121.9 ms; its longest observed Long Task was only 178 ms. A heartbeat gap can include scheduling delay and must not be described as a single 1.12-second JavaScript task. Large 24 MiB SVG/native project imports, manual Save/cancel, text-worker cancellation, heightfield cancellation, removal-grid work, and the 2,000-object open/Preview checks passed. Their complete test durations include setup and are not operation benchmarks.

The final dedicated full-app probe warmed source/fixture imports, explicitly waited for idle worker creation before switching views, disabled Playwright trace recording, owned its server, and waited for `data-viewer-state="ready"`. Initial timing includes installing the project, idle worker startup, switching views and renderer readiness; it is not pure click-to-view latency. Three unprofiled samples gave:

| Full desktop-renderer interaction, 31-region mixed fixture | Median | Range |
| --- | ---: | ---: |
| G-code 3D view rendered ready | 2,228 ms | 2,222–2,315 ms |
| Refresh rendered ready | 371 ms | 358–457 ms |
| Initial phase maximum heartbeat gap | 98.9 ms | 89.6–102.7 ms |
| Initial phase longest Long Task | 72 ms | 59–79 ms |

No Long Tasks were observed during these Refresh phases. A fourth CPU-profiled run is retained separately and excluded from medians. Its sampled main-thread work included Three.js first-use shader setup and garbage collection; worker CPU was not profiled. This identifies remaining interaction costs but does not qualify displayed 60 fps. The original second-scale gap did not repeat under this warmer measurement setup; cold development loading and host scheduling remain possible contributors, not a proven root cause.

Core regression checks: **9 files, 32 passed, 1 skipped**. Connected-script V-carve compilation/emission took 6,004 ms in the instrumented serial algorithm harness: 5,668 ms in region planning and 255 ms in emission. It retained the exact 1,100,098-byte output and SHA-256 `6213711b652de729c1d4c57f905817bf39eab2ef86e8d8a1627f37ba20a6dbc6`. This is not a worker-pool speed measurement. The 1.9-megapixel thick-stroke centreline trace took 944 ms; fill/mask and contour-indexing regression checks passed.

Multiple-anchor curve editing does copy N segments for each selected anchor (`path-node-edit-geometry.ts:164` → `curve-edit.ts:41`). However, the measured 100,000-segment fixture took 1.8 ms for one anchor and 5.6 ms for 100 anchors. This ranks below the confirmed larger costs; drawing handles and the rest of the drag frame were excluded. Current UI selection is incremental, so selecting every node is not presented as a normal gesture.

The existing native-worker browser component pipeline also completed warmup plus three repeat samples with stable output hashes:

| Component pipeline | Median | Range |
| --- | ---: | ---: |
| 50,000-contour SVG, fill output, preview and parse | 5,667 ms | 5,233–6,340 ms |
| Sparse 4096² image import, preview/commit trace, vector/raster output | 4,844 ms | 4,026–5,236 ms |
| Same image through paged IndexedDB import | 5,475 ms | 5,212–5,916 ms |

For the SVG case, G-code emission was the largest median stage at 2,085 ms, followed by worker import at 1,692 ms and output parsing at 826 ms. It emitted 5,955,318 bytes / 675,704 lines. This harness invokes component APIs, including some synchronous compiler/emitter calls, rather than reproducing the application's scheduling; its timings are not UI freeze measurements. It deliberately disables travel optimisation and inside-first ordering. Trace preview and commit use different grids (2048² and 2559²), so their two worker calls are not evidence of duplicate identical tracing.

Source-only follow-ups: repeated CNC input copies through the broker, trace/DXF result materialisation, per-node overlay drawing, and repeated open-Fill diagnostics. These need targeted timing before claiming an impact or prioritising a rewrite.
