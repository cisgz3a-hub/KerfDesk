### R100-01 — Classify Marlin stored macros at both command boundaries

**Locations:** `src/core/external-program/storage-command-check.ts:56–65`; `src/core/devices/positioning-light.ts:65–69` and `:219–224`.

The #1410 stored-program guard omits **M810–M819**. A probe through the production normalizer, Inspector, external review and `prepareExternalRun` accepts `G1 X10 F600`, `M810`, `M5` and returns `ready`; its Frame envelope covers only X0–X10. A configured macro can move farther. A self-contained example defining `M810 G1 X120 F600` before invoking it also returns `ready`, with a point Frame. Generic unsupported-command warnings are shown: this is a failure to apply the specific existing stored-program refusal, not a claim that the program is silently certified.

On Marlin builds with `GCODE_MACROS`, an M810 command with arguments stores the command string and a bare M810 executes it. This is confirmed in the [pinned Marlin 2.1.2.8 implementation](https://github.com/MarlinFirmware/Marlin/blob/2.1.2.8/Marlin/src/gcode/feature/macro/M810-M819.cpp). ADR-630 Amendment 5 already excludes stored programs that cannot be reviewed and framed.

The same macro family is absent from generic positioning-light validation. A Marlin mapping with On=`M810`, Off=`M811` is accepted and dispatched as an accessory command, although it can invoke stored motion. This older omission was retained by #1386; it is not the stock Falcon dot path. ADR-603 excludes known movement from separate-light commands.

**Repair:** extend controller-aware stored-program classification to these macros in both entry points. Add canonical external-Run and light-mapping regressions while preserving documented accessory commands. **Evidence:** `machine/macro-probe.mjs`, `machine/macro-probe-final.log`. No controller or hardware was operated; the macro capability is conditional on the firmware build and stored content.

### R100-02 — Retain ownership of camera nudge requests and results

**Locations:** `src/ui/camera/calibrate/NudgeSteps.tsx:96–104`, `:149–150`; `src/ui/camera/calibrate/nudge-actions.ts:99–107`.

A pending Take photo operation can finish after the nudge wizard is closed and full Camera setup is opened. Its completion replaces that new wizard's step with `nudge-result`. Separately, the saved nudge result carries only an offset; Fix applies it to the current project/calibration. A production-wizard probe obtains a 2 mm result, replaces the document and epoch, then observes Fix shifting the replacement calibration by 2 mm.

This can persist a calibration change unrelated to the ring and photograph that were measured, affecting later artwork placement. The regular calibration ownership repair in #1425 does not cover the separate nudge path. #1427 does not change these files.

**Repair:** bind capture and result to the wizard session, document epoch, camera source and exact calibration/profile; check ownership both after capture and when applying Fix. Retain the measurement's bed-centre snapshot. **Evidence:** first two assertions in `desktop.probe.test.tsx` and `desktop-probe-final3.log`. The detector/capture is mocked; the wizard, store and apply model are production code. This is not a real-camera or native file-picker trial.

### R100-03 — Prevent an older refresh from publishing last

**Location:** `src/ui/camera/helpers/refresh-picture.ts:31–39`.

Refresh A starts, refresh B starts and completes with a newer picture, then A completes and replaces B. The helper only checks that the same camera object is still running; both requests return `refreshed`. Keyboard refresh and automatic after-job refresh can overlap on slow JPEG/RTSP captures.

The held bed view used for placement can therefore revert to an earlier image after the operator has refreshed it. **Repair:** make the newest request own publication, or serialize/coalesce refreshes, and respect later Live/held-image changes. Consider consistent ownership across the manual Refresh path too. **Evidence:** third production-helper assertion in `desktop.probe.test.tsx`, passing by observing the incorrect order in `desktop-probe-final3.log`. No live camera was used.

### R100-04 — Redact whole quoted values, including escaped quotes

**Location:** `src/ui/support/support-report-redaction.ts:32–33`.

The actual support-report formatter transforms synthetic JSON `{"password":"head\"SECRET-SUFFIX"}` into a value that still contains `SECRET-SUFFIX`. The pattern treats an escaped quote as the value's end. It also leaves `wifi password="SECRET WITH SPACE"` unchanged because the key/value pattern excludes an opening quote. Escaped quotation marks are valid within JSON strings under [RFC 8259 section 7](https://datatracker.ietf.org/doc/html/rfc8259#section-7).

Both the Machine console and Desktop log sections retain these secrets. Sharing the exported report would disclose them despite its password-removal feature. The probe uses only synthetic strings and sends no report.

**Repair:** parse structured JSON where appropriate or scan escaped/quoted values correctly, and handle quoted key/value forms. Add complete-formatter regressions. **Evidence:** `document-redaction-probe.mjs` and `document-redaction-probe.json`. The redactor is unchanged by open #1427.

### R100-05 — Recognize the controller's accepted password aliases everywhere

**Locations:** `src/ui/support/support-report-redaction.ts:23–31`; `src/core/controllers/controller-password-settings.ts:29–35` on the frozen main.

The actual report preserves complete synthetic credentials in `[Sta/Password]SYNTHETIC-WIFI-PASSWORD` and `$ESP101=SYNTHETIC-ALIAS-PASSWORD`. FluidNC accepts bracket/dollar command syntax and descriptive/compatibility names, with `Sta/Password` and `ESP101` naming the station password. These routes were checked in the official [command parser](https://github.com/bdring/FluidNC/blob/main/FluidNC/src/ProcessSettings.cpp) and [Wi-Fi settings declarations](https://github.com/bdring/FluidNC/blob/main/FluidNC/src/WebUI/WifiConfig.cpp).

The report also leaks `$075=...` and `$74.999999=...`. The pinned grblHAL [system parser](https://github.com/grblHAL/core/blob/4ec1ae44b857a70d2f9298344feac4b43ed0eb6b/system.c#L1208-L1210) reads a float, checks integer proximity, then casts the setting ID. Its [number parser](https://github.com/grblHAL/core/blob/4ec1ae44b857a70d2f9298344feac4b43ed0eb6b/nuts_bolts.c#L249-L316) maps the leading-zero form to 75; independently reproducing its single-precision operations also maps 74.999999 to 75. This is source analysis and numerical reproduction, not a firmware execution test.

The report duplicates a narrower masker instead of using the shared controller masker. Latest #1427 adds numeric-alias handling to the shared code, but leaves the report unchanged and still misses the named-bracket/dollar-ESP FluidNC forms. #1427 did not introduce this defect.

**Repair:** use one controller-aware masker for diagnostic reports and visible-console copies, covering accepted numeric and FluidNC aliases. Keep intentional restore exports distinct. **Evidence:** `document-redaction-probe.json`, `numeric-password-alias-evidence.json`, and the reviewed #1427 delta `pr1427-head-refresh.json`.

### R100-06 — Report stale tile files when bit counts change

**Location:** `src/ui/app/tile-folder-check.ts:34–50`.

An existing folder contains `job_tile-r1-c1_bit-1-of-2.nc` and `job_tile-r1-c1_bit-2-of-2.nc`. Exporting that tile with one bit or three bits returns empty `replaced` and `earlier` lists. The new names are written and the obsolete executable files remain without a warning.

The implementation handles the documented single-file-to-multiple-bits transition, but not these further changes. This is P3 because it does not automatically select or execute the old files; their names still show the old bit count and ordinary review/Frame requirements remain.

**Repair:** track the prior export set or identify and warn about all earlier same-job tile files. Do not silently delete user files. **Evidence:** `root-tile-folder-probe.mjs`, `root-tile-folder-probe.log`. #1427's motion-count repair does not address folder history.
