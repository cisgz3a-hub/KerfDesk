## P3-1 — `isToolChangeLine`'s `;`-comment strip is defeated by the trailing newline (latent bug + false comment)

`splitLines` appends `\n` to every queued line ([streamer.ts:148](../../src/core/controllers/grbl/streamer.ts)), so `isToolChangeLine` always receives e.g. `"M0 ; change bit\n"`. Its strip `/;.*$/` has no `m` flag; in JS `$` (single-line) matches **only at true end-of-string, never before a trailing `\n`** (unlike Python), and `.` doesn't cross `\n` — so the match fails, nothing is stripped, and the function returns **false** ([streamer.ts:127](../../src/core/controllers/grbl/streamer.ts)).

**Empirically confirmed** (ran the exact function in node): `isToolChangeLine("M0 ; change bit\n") === false`, while `"M0\n"` → true and `"M0 (change bit)\n"` → true (the paren strip `/\(.*?\)/g` is global, needs no `$`). The function's own comment ([streamer.ts:123](../../src/core/controllers/grbl/streamer.ts)) explicitly claims "so an imported `M0 ; change bit` still matches" — it does not. **Consequence if reached:** `fillBuffer` never detects the M0, so it streams to GRBL, which enters a feed **Hold** — the exact state from which the operator cannot jog/probe/G92 to re-zero the new bit (the failure the tool-change hold exists to prevent).

**Why P3 (latent):** the only stream fed with `toolChangePause=true` is KerfDesk's own CNC emitter output, which pushes a **bare** `M0` ([cnc-grbl-transitions.ts:69](../../src/core/output/cnc-grbl-transitions.ts)) with its human label on a *separate* preceding `;` comment line (filtered out as a full-line comment). Imported `.nc` programs are preview-only, never streamed. The bug goes live if imported `.nc` streaming is ever enabled or the emitter ever appends an inline `;` comment to an M0. **Secondary drift:** [laser-job-actions.ts:296](../../src/ui/state/laser-job-actions.ts) sets `toolChangePause` for **every** CNC job regardless of provenance, contradicting the `StreamerState` doc ([streamer.ts:74-78](../../src/core/controllers/grbl/streamer.ts)) that scopes it to KerfDesk-emitted jobs and says imported M0s "must stream through unchanged" — harmless only because imported `.nc` never streams today, but it widens the blast radius. Fix: strip to end-of-line (`/;[^\n]*/`) or trim the terminator before the regex, and correct the comment.

## P3-2 — Recovery upper-bound byte tally counts UNtrimmed raw lines while the streamer sends trimmed lines

The sendable *predicate* (`isSendableGcodeLine`) is correctly shared and does not drift — but the **byte-per-line accounting** does. The streamer trims every line before terminating (`splitLines`: `.map(l => l.trim())` then `${l}\n`, [streamer.ts:145-148](../../src/core/controllers/grbl/streamer.ts)), so a sent line occupies `trim(raw).length + 1` bytes. `lastPossiblyExecutedRawLine` instead computes `bytes = line.length + 1` on the **untrimmed** `rawLines[raw-1]` from `gcode.split('\n')` ([cnc-resume-point.ts:122](../../src/core/recovery/cnc-resume-point.ts)), and its comment ([:107-108](../../src/core/recovery/cnc-resume-point.ts)) asserts sendable lines are "emitted verbatim plus a single `\n`" — which is false (the streamer trims). Any raw line carrying leading/trailing whitespace (indented CAM output) or a surviving `\r` (Windows CRLF — `split('\n')` keeps it, the streamer's `.trim()` drops it) over-counts ≥1 byte.

**Correctly scoped as P3:** this over-counts bytes → the RX-budget estimate exhausts after *fewer* lines → reports a `lastPossiblyExecutedRawLine` **lower** than what actually fit — the module's *stated safe direction* (an earlier boundary only re-cuts already-cleared kerf, [cnc-resume-point.ts:12-15](../../src/core/recovery/cnc-resume-point.ts)), and it affects only the informational upper bound, never the load-bearing proven/first-unproven lower bound. Fix: trim before measuring so the tally mirrors the streamer's on-wire bytes.

## P3-3 — Two divergent M0 detectors: the streamer's `isToolChangeLine` vs the caller's `countM0Boundaries`

`countM0Boundaries` matches `line.trim().toUpperCase() === 'M0'` — **bare M0 exactly** ([laser-job-actions.ts:335](../../src/ui/state/laser-job-actions.ts)) — while `isToolChangeLine` also holds on M00/M1/M01 and strips paren comments. The tool-plan-vs-boundary count check ([laser-job-actions.ts:322](../../src/ui/state/laser-job-actions.ts)) uses `countM0Boundaries`. If a boundary were ever emitted as `M1`/`M00`/`M0 (comment)`, the streamer would hold at it but `countM0Boundaries` would not count it — a spurious `TOOL_CHANGE_PLAN_MISMATCH`, or a drift in the label/toolId slice offsets. Latent (the emitter emits bare M0, which both agree on), but two independent predicates for the same concept invite exactly this class of drift. Fix: have the caller reuse `isToolChangeLine`.

## Verified clean (checked hard, no defect)

- **Terminal absorption (H5):** trailing `ok`s after an `error:N`/`ALARM` cannot promote the stream back to `done` — `isTerminal` short-circuits the status in `onAck` while still freeing bytes. Correct and tested.
- **Alarm wipes in-flight (F1):** an `alarm` ack clears all in-flight lines and `inFlightBytes`, so the store's ack-attribution can't later claim an untracked `$X`/`M9` ack for the dead stream. Correct.
- **Done-promotion is guarded:** `onAck` promotes to `done` only when not paused/tool-change/terminal AND both in-flight and queue are empty; a paused stream draining its held tail stays `paused` (`resume` completes it). No mis-promotion of a rejected or unfinished stream.
- **Empty-in-flight error/alarm → terminal:** an `error`/`alarm` arriving with nothing in flight still makes the stream terminal, so `resume` can't stream the queue into a locked controller. Correct and tested.
- **Oversized-line freeze is guarded** (my own check): a line longer than the RX buffer would silently freeze `step()`, but `assertGcodeFitsController` runs `findOversizedLine` and throws in `prepareStartBoundary` ([laser-job-actions.ts:194,276-284](../../src/ui/state/laser-job-actions.ts)) **before** `createStreamer` ([:125,296](../../src/ui/state/laser-job-actions.ts)) — the M13 requirement holds.
- **The sendable predicate is consistently shared** by `splitLines`, `findOversizedLine`, and the recovery mapper (`job-checkpoint.ts`, `cnc-resume-point.ts`) — so the acked-count↔raw-line mapping is correct (only the *byte* tally drifts, P3-2, not the line-count predicate).
- **UTF-16 `.length` vs UTF-8 byte count (a raised finding, refuted):** the byte tally uses `line.length` (UTF-16 units), but KerfDesk emits pure-ASCII G-code and full-line comments are dropped, so no non-ASCII char reaches a sent line — `.length === byteLength` in practice, no RX overflow.
- **Purity:** the streamer is a pure reducer — no clock, random, console, throw-for-control-flow, or mutable module state; every transition returns a fresh state.
