## P2-1 — Nested INSERT/MINSERT expansion has no aggregate budget (decompression-bomb OOM from a tiny file)

INSERT expansion is bounded **only per-grid** (`isDxfInsertGridWithinBudget`: `columns*rows ≤ MAX_MINSERT_INSTANCES = 10_000`, [dxf-insert-grid.ts:18-20](../../src/io/dxf/dxf-insert-grid.ts)) and **per-depth** (`MAX_INSERT_DEPTH = 8`, [dxf-expand.ts:179](../../src/io/dxf/dxf-expand.ts)). There is **no running total** of emitted polylines/points anywhere in the DXF path. `expandInsert` recurses into a block's children ([dxf-expand.ts:197](../../src/io/dxf/dxf-expand.ts)) and then `placeInsertInstances` **replicates every child polyline across `rows*columns`** ([dxf-expand.ts:226-249](../../src/io/dxf/dxf-expand.ts)). Because a MINSERT's child block can itself be a MINSERT, the output count is the **product** of grid sizes down the chain — up to `10_000^depth` (≈10³² at depth 8) output polylines, while every individual grid passes the per-grid budget.

**Verified minimal exploit (~20 tags):** `BLOCK B0` = one `LINE`; `BLOCK B1` = one `INSERT` of B0 with `70=100, 71=100` (grid 10 000); `ENTITIES` = one `INSERT` of B1 with `70=100, 71=100`. Trace: inner MINSERT emits `1×10 000 = 10 000` polylines; outer replicates those across `10 000` instances = **10⁸ polylines / 2×10⁸ points at depth 2 of 8** — guaranteed tab OOM/hang and loss of the maintainer's unsaved scene. Each grid is exactly `10 000 ≤ 10 000`, so no guard fires.

**The one existing guard is on the wrong axis:** `dxf-import-action.ts:38-40` gates on `confirmOversizeImport` = **input file bytes** (`MAX_IMPORT_FILE_BYTES = 25 MB`, `import-size-guard.ts:9`). A compression-bomb DXF is a few KB — it passes without even a confirm prompt — and `parseDxf` runs **synchronously on the main thread** ([dxf-import-action.ts:41](../../src/ui/app/dxf-import-action.ts)), so the OOM happens during expansion before any output size can be measured.

**Contrast (the fix pattern already exists):** the SVG importer enforces global `SVG_IMPORT_LIMITS.polylines` (50 000) and `.points` (250 000) throw-caps *during* import ([svg-import-budget.ts:31-36](../../src/io/svg/svg-import-budget.ts)); the DXF importer has no equivalent aggregate budget. This is the "DXF MINSERT OOM" class from the 2026-07-13 PR#58 audit: the per-grid cap was added, the aggregate cap never was. Fix direction: thread a running polyline/point counter through `expandEntities`/`placeInsertInstances` and abort (skip + note) when it exceeds a global budget, mirroring the SVG throw-cap.

## P3-2 — INSERT transform params bypass the `hasUnreadableGeometry` gate every other entity passes

In `expandEntities`, the INSERT branch runs and `continue`s at [dxf-expand.ts:101-107](../../src/io/dxf/dxf-expand.ts) **before** the `hasUnreadableEntityGeometry` skip at line 111 — so an INSERT's own transform tags (insert point 10/20, scale 41/42, rotation 50, spacing 44/45) are never subjected to the finite/magnitude gate that gates every direct entity. `placeInsertInstances` reads them via `firstNumber → parseNumber`, which **coerces non-finite to a fallback** (0, or 1 for scale). Two consequences: (a) a non-finite insert point (`code 10 = "NaN"`) silently mis-places the block at the origin instead of being skipped+reported like any other entity's non-finite coordinate; (b) a large-but-finite value (`10 = 1e12`, or huge spacing on `44`) passes uncapped, defeating `DXF_COORDINATE_MAGNITUDE_MM` ([dxf-entities.ts:233](../../src/io/dxf/dxf-entities.ts)) whose stated purpose is import-boundary rejection. Case (b) is backstopped by bed-bounds preflight before machine motion; case (a) is a genuinely silent fidelity defect no existing safeguard catches.

## P3-3 — Import `notes` are computed but never surfaced to the operator (silent geometry loss with a "success" toast)

`parseDxf` returns `result.notes` ([parse-dxf.ts:37,72](../../src/io/dxf/parse-dxf.ts)), but `importDxfFiles` builds its toasts **only** from `result.skippedSummary` and `result.pathCount` and **never reads `result.notes`** ([dxf-import-action.ts:46-57](../../src/ui/app/dxf-import-action.ts)). Several drop paths report *only* via a note with no skipped-counter bump: **INSERT references an unknown block** ([dxf-expand.ts:172-178](../../src/io/dxf/dxf-expand.ts), empty skipped map) and **INSERT nested deeper than 8** ([dxf-expand.ts:179-185](../../src/io/dxf/dxf-expand.ts), empty skipped map). Result: geometry inside a too-deeply-nested or unresolved block is **silently discarded** and the operator still gets "Imported N paths" with no indication anything was lost. Contrast: the G-code opener *does* surface its notes (`gcode-open-action.ts`). Surface `result.notes` in a toast/log like the sibling importers.

## P3-4 — `$INSUNITS` table omits standard units (miles=3, kilometers=7) → silent wrong-scale import

`INSUNITS_TO_MM` maps `{0,1,2,4,5,6,9,10,13,14}` but omits several standard DXF enum values, including **3 = miles** and **7 = kilometers** (also 8/11/12/15-20) ([parse-dxf.ts:43-54](../../src/io/dxf/parse-dxf.ts)). `unitScale` falls back to scale 1 (mm) for these ([parse-dxf.ts:131-134](../../src/io/dxf/parse-dxf.ts)), so a kilometer-authored drawing imports **1,000,000× too small** and a mile-authored one ~1.6×10⁹× too small. **This compounds with P3-3:** the only mitigation is the "Unrecognized $INSUNITS N — assuming millimeters" note, which P3-3 shows is never displayed — so the operator sees "Imported N paths" with invisibly wrong-scaled geometry. Add the missing conversions (7 → 1 000 000, 3 → 1 609 344, …).

## P3-5 — Coordinate-magnitude cap is type-confused on code 40 (SPLINE knot / ELLIPSE ratio, not a length)

`hasUnreadableGeometry` treats code 40 as a scaled length (`DXF_SCALED_LENGTH_CODES` includes 40, [dxf-entities.ts:229,243-248](../../src/io/dxf/dxf-entities.ts)), but code 40 is a **knot value** for SPLINE ([splineToPolyline:144-150](../../src/io/dxf/dxf-entities.ts)) and a **radius ratio** for ELLIPSE ([ellipseToPolyline:110](../../src/io/dxf/dxf-entities.ts)), neither a length. A valid SPLINE with a large knot parameter (`> 1e6/scale`) is falsely rejected as "unreadable" and skipped. Reachability is marginal (knots are usually small/normalized), but the cap semantically mis-classifies the code. Fix direction: scope the magnitude cap to codes that are lengths *for the entity being converted*, or exclude 40 from the length set and cap radius separately.

## P3-6 — `transformCurve` / `transformNormalizedCurve` lack `assertNever` exhaustiveness

Both curve transforms branch on `segment.kind === 'line'` and `=== 'cubic'` with explicit `if`s, then fall through to an **unguarded final `return` that assumes the elliptical-arc variant** (and even mutates `sweep: !segment.sweep`) ([dxf-expand.ts:253-269](../../src/io/dxf/dxf-expand.ts); [parse-dxf.ts:214-233](../../src/io/dxf/parse-dxf.ts)). `PathSegment` has three variants today (`scene-object.ts:38`); if a fourth is added, TypeScript will **not** flag these sites — a new variant is silently mistransformed as an arc rather than caught at compile time, exactly the failure CLAUDE.md's discriminated-union `assertNever` rule exists to prevent.

## Verified clean (checked hard, no defect)

- **INSERT recursion cycles terminate:** the depth-8 guard bounds block self-reference/mutual recursion (it just doesn't bound per-level grid multiplication — that's P2-1).
- **Bulge/arc/ellipse sampling has no finite-input divide-by-zero:** `bulgeSegment` guards `chord === 0 || bulge === 0` before dividing by `sin`/`tan`; the remaining `sin(|sweep|/2)` and `tan(sweep/2)` are non-zero for finite non-zero bulge.
- **Zero/negative-radius CIRCLE and ARC are skipped** (`!(radius > 0)`), and spline sampling is bounded (`MAX_SAMPLES = 2048`).
- **Non-finite *direct-entity* coordinates are rejected** at the import boundary (`hasUnreadableGeometry`, mirroring SVG's `finiteNumber`) — the gap is only the INSERT-transform bypass (P3-2).
- **Section/block/vertex walkers, color resolution (BYBLOCK inheritance, true-color 420, ACI), and the Y-flip + bbox normalization** are correct on read; no mis-grouping or dropped geometry found in the parser core.
- **Skipped *entity types* (TEXT/HATCH/MTEXT/DIMENSION/…) are counted and reported** via `skippedSummary` — a documented 2.5D scope limitation, not a silent drop (the silent-drop problem is confined to the note-only paths in P3-3).
