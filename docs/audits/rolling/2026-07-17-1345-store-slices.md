- **Scope:** the central state layer — `src/ui/state/store.ts` (slice composition), `store-actions.ts` (project mutations + undo/redo + dirty tracking), `laser-store.ts`, and the ~30 `*-actions.ts` slice factories. ## Headline

**Zero P1/P2.** The store's core immutability discipline holds: every slice action builds a fresh local (array/object) and spreads it into new state via `set()` — no in-place mutation of an existing state value, no direct `state.x = …` assignment anywhere (my own scan + the immutability finder both came back clean). The six findings are one real dirty-tracking bug, a discriminated-union modeling nit, the module-mutable rule question, an exhaustiveness gap, a near-cap file, and a test gap.

## P3-1 — `cancelInteraction` leaves `dirty = true` after a fully-rolled-back drag

The interaction lifecycle: `beginInteraction` snapshots `pendingUndo: s.project` (no dirty change); `setObjectTransform` during the drag sets `dirty: true`; `cancelInteraction` (Esc mid-drag) restores `project: s.pendingUndo` and clears `pendingUndo` — **but never resets `dirty`** ([store-actions.ts:335-336](../../src/ui/state/store-actions.ts)). So a drag that starts on a **clean** project, moves an object (dirty→true), then is cancelled, restores the project byte-for-byte to the pre-drag snapshot yet leaves it flagged **dirty**. The operator sees an unsaved-changes indicator (and a discard prompt on close) for a drag that "never happened." Not data loss — the project content is correct — but the dirty flag lies. `beginInteraction` snapshots only the project; the fix is to also snapshot and restore the pre-interaction `dirty` value on cancel.

## P3-2 — `probeBusy` boolean duplicates state already encoded by `controllerOperation.kind === 'probe'`

`probeBusy: boolean` ([laser-store.ts:114](../../src/ui/state/laser-store.ts)) is set true/false alongside the `controllerOperation` discriminated union ([laser-probe-actions.ts:110,148](../../src/ui/state/laser-probe-actions.ts)), duplicating information the union already carries (`controllerOperation.kind === 'probe'`). CLAUDE.md's "State — discriminated unions only" exists precisely to avoid a second flag that can drift from the tag: because `probeBusy` is set independently, an impossible combination (`probeBusy === true` while `controllerOperation.kind !== 'probe'`, or vice versa) is representable and must be kept in sync by hand at every transition. The clean model derives probe-busy from the union (`operation.kind === 'probe'`) rather than storing a parallel boolean.

## P3-3 — Module-level mutable `let`/singletons violate "no module-level mutable variables… never a singleton"

Three module-level mutables in the state layer, scoped precisely against ADR-050 (which the review surfaced — it authorizes *input-identity memoization caches in `core/job`* and the lazy WASM/font/tracer singletons, but explicitly bans "any other module-level mutable"):

- **`let nextProbeTransactionId = 1`** ([laser-probe-actions.ts:44](../../src/ui/state/laser-probe-actions.ts), reassigned `++`) — a monotonic ID counter, **outside** the ADR-050 carve-out (not a memoization cache or a lazy resource). Genuine violation. Low functional risk (the token is only compared for self-equality to reject stale probe completions), but it is process-global and never reset, so a test asserting the literal id (it appears in log strings) is execution-order-coupled. Clean fix: move the counter into the store slice or derive the token from `crypto.randomUUID()`.
- **The `refs` module-global bag** ([laser-store.ts:268](../../src/ui/state/laser-store.ts)) — mutated in place throughout the laser actions. **Defensible carve-out** (it holds non-serializable live I/O handles — `SerialConnection`, poll timers, unsubscribe closures — that deliberately cannot live in immutable state, and every mutation is identity-guarded), but being module-**global** it is shared across store instances: the code itself acknowledges this hazard (it already moved `forgetFinalizations` to a store-local `WeakMap` "because a module-global WeakMap can couple independent store instances that share a test port"), yet the `refs` bag remains module-global.
- **`let fallbackSessionId`** ([autosave.ts:64](../../src/ui/state/autosave.ts)) — a lazy-init (`??=`, assigned once) process-local fallback used only when `sessionStorage` is unavailable (SSR/tests). Most defensible (initialize-once, never reassigned); autosave is free functions with no per-instance home.

**The ask** (like the test-boundary exemption from iteration 6): either extend ADR-050 to document these UI-state patterns as an authorized carve-out, or move the counter/`refs` to per-store-instance homes. As-is they violate the literal rule with no ADR.

## P3-4 — `LaserControllerOperation` kind pattern-match lacks an `assertNever` default

The `kind` match on `LaserControllerOperation` ([laser-controller-operation.ts:64](../../src/ui/state/laser-controller-operation.ts)) has no `assertNever` default arm, so a new operation variant would not be caught at compile time — the exact failure CLAUDE.md's discriminated-union rule mandates `assertNever` to prevent (same class as the CNC/DXF/streamer/recovery findings).

`store-actions.ts` measures **388 counted code lines** (417 raw), over the 250 soft limit and within a small edit of the **400 counted hard cap** that ESLint fails the build on ([store-actions.ts](../../src/ui/state/store-actions.ts)). Not a violation today, but the next feature added here risks tripping CI; the interaction/undo/dirty logic is a natural extraction. ## P3-6 — Test gap: the `HISTORY_DEPTH = 50` undo/redo depth cap is never exercised

`pushUndo` caps the undo stack at `HISTORY_DEPTH = 50` via `slice(-HISTORY_DEPTH)` ([scene-mutations.ts:35,79-81](../../src/ui/state/scene-mutations.ts)), but no test pushes past 50 to assert the oldest entry is dropped and the cap holds — a silent regression (e.g. an off-by-one or a removed cap causing unbounded memory growth) would pass the suite.

## Verified clean (checked hard, no defect)

- **Immutability holds:** every slice action's `.push`/build targets a **fresh local** (`copies`, `out`, `parts`, `objects`, `units`, `polylines`, …) spread into new state, never an existing state value; zero `state.x = …` in-place assignments across the `*-actions.ts` files (my own grep + the immutability dimension). `endInteraction` correctly pushes undo and no-ops when `pendingUndo === s.project`.
- **ADR-050 legitimately covers** the `core/job`/`core/text`/`core/trace` lazy memoization singletons (`opentypePromise`, `tracerPromise`, worker instances) — those are *not* violations; only the two UI-state mutables (P3-3) fall outside it.
- **The variable-stream observer is re-arm-guarded** (`armVariableStreamAdvancement` calls `cancelVariableStreamAdvancement()` first) — no observer leak on re-install (my own check).
- **`store.ts` is under the counted size cap**; the store is properly decomposed into ~30 single-responsibility slice factories per ADR-015.

- The full ~30 slice factories were sampled by the finders, not each read end-to-end; a deeper per-slice pass could surface more of the same P3 class.
