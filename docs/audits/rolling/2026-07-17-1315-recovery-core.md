## P3-1 — Non-finite `ackedLines` escapes the clamp and resumes at the LAST pass (skip-material direction; guarded upstream)

`const acked = Math.min(Math.max(Math.floor(args.ackedLines), 0), sendableTotal)` ([cnc-resume-point.ts:73](../../src/core/recovery/cnc-resume-point.ts)) does not sanitize `NaN` as its clamp shape implies — `Math.floor(NaN)=NaN`, and both `Math.max`/`Math.min` propagate it, so `acked = NaN`. Then `proven = NaN`, the `proven >= sendableTotal` early return is skipped (`NaN >= x` is false), `rawResumeLine(gcode, NaN)` falls through to **`lastSendableRaw`** (the `sendableSeen > NaN` guard is always false, [job-checkpoint.ts:142-144](../../src/core/recovery/job-checkpoint.ts)), and `spans.find(lastRawLine >= lastSendableRaw)` resolves to the **final** span → `resume-at-pass` at the last pass, **skipping every earlier uncut pass** — the unsafe direction, on the safety-critical mapping.

**Why P3 (latent, guarded at three upstream layers):** the sole non-test caller passes `capsule.ackedLines` from a validated checkpoint, and every write path rejects non-finite: `parseJobCheckpoint`'s `isNonNegativeInteger` ([job-checkpoint.ts:180](../../src/core/recovery/job-checkpoint.ts), `Number.isInteger` rejects NaN), `clampProgress`'s explicit `if (!Number.isFinite(value)) return 0` (`recovery-slot-mutations.ts`), and the persistence `isProgressRecord` gate. So NaN cannot reach the branch today. But the mapping is safety-critical and undefended *in-function* — a single in-function `Number.isFinite(args.ackedLines) ? … : 0` would make the recut-never-skip invariant hold unconditionally rather than by upstream contract. (`+Infinity` clamps correctly to `sendableTotal`, `-Infinity` to 0; only `NaN` escapes.)

## P3-2 — Supervised recovery digest omits the physical-setup fingerprints the automatic package binds

The **automatic** recovery capsule hashes `machineProfileFingerprint`, `wcsFingerprint`, `jobOriginFingerprint`, `stockFingerprint`, and `fixtureFingerprint` ([cnc-recovery-package.ts:119-124](../../src/core/recovery/cnc-recovery-package.ts)), so its exact-match digest changes if the physical setup changes. The **supervised** capsule — the path that actually produces an executable recovery job — hashes only source-gcode, recovery-gcode, the plan, the runway profile, and the review/proof IDs ([cnc-recovery-package.ts:129-149](../../src/core/recovery/cnc-recovery-package.ts)); **no machine/WCS/origin/stock/fixture fingerprint**. The plan's recovery polyline coordinates are frozen at generation time, so re-running the same supervised capsule after re-zeroing to a different datum yields a **byte-identical digest** executed against a different physical origin — the clear-cutter policy's exact-match check ([cnc-recovery-policy.ts:183-185](../../src/core/recovery/cnc-recovery-policy.ts)) can't distinguish it.

**Why P3 (mitigated):** the clear-cutter policy independently requires `position.kind === 'requalified'` and a complete operator review with fresh cleared-path + completed-prefix proofs ([cnc-recovery-policy.ts:181,184-201](../../src/core/recovery/cnc-recovery-policy.ts)); a genuine stock/origin change would fail those proofs. Still, binding the setup fingerprints into the supervised digest (as the automatic package already does) would make the digest self-sufficient rather than relying on the surrounding policy to catch a setup change.

## P3-3 — `cutSegmentCount` branches on `CncPass.kind` without an `assertNever` default

`cutSegmentCount` handles only `'contour'` and `'path3d'` explicitly, then falls through to `return 1` ([cnc-recovery-manifest.ts:144-148](../../src/core/recovery/cnc-recovery-manifest.ts)). `CncPass` is a 4-variant union (`contour|path3d|arc|helical-contour`, [job.ts:138](../../src/core/job/job.ts)), so `'arc'` and `'helical-contour'` silently hit `return 1`. Behaviorally safe today, but CLAUDE.md's discriminated-union rule requires an `assertNever` default so a new variant is caught at compile time (same class as the CNC/DXF/streamer findings).

## P3-4 — `KINEMATIC_DIVISOR` is conflated as a minimum-point-count threshold

`KINEMATIC_DIVISOR` (=2) is defined as the `2` in the stopping-distance formula `v²/(2a)` and used as such at [cnc-contour-runway-geometry.ts:39](../../src/core/recovery/cnc-contour-runway-geometry.ts), but is **reused** at [line 111](../../src/core/recovery/cnc-contour-runway-geometry.ts) as a minimum polyline length (`points.length >= KINEMATIC_DIVISOR`) — a semantically unrelated concept sharing one constant. A distinct `MIN_CONTOUR_POINTS = 2` would express intent and decouple the two (a future kinematic change to the divisor must not silently move the min-point threshold).

## Verified clean (checked hard, no defect)

- **Recut-never-skip holds:** through the shipped path, `proven = acked − reserve` (reserve ≥ 32) keeps `firstUnprovenRawLine` at or before the physical frontier, so the resume pass re-cuts and never skips — no acked/reserve/span arrangement breaks it except the NaN case (P3-1), which is blocked upstream.
- **`cnc-resume-point.ts:76` is reachable and benign** (my seed, refuted): it fires only for a zero-sendable (comment-only) program and correctly returns `after-last-pass`; it is not dead code, and `after-last-pass` is separately reachable and tested via the `defaultSpan === undefined` path.
- **`parseJobCheckpoint` is strict:** rejects future-schema, truncated, tampered (`sendableLines ≤ fingerprint.lines`, `ackedLines ≤ sendableLines`), non-integer, and malformed jobOrigin/interruption — a bad checkpoint reads as null and is discarded, never resumed from garbage.
- **`spansAreValid`** enforces ascending, non-overlapping, in-range spans; the checkpoint fingerprint (FNV-1a + chars + raw lines) plus the resume-time recompile-and-compare makes a divergent recompile refuse; `advanceJobCheckpoint` is monotonic; the sendable-vs-raw numbering discipline is shared consistently via `isSendableGcodeLine`.
- **Purity:** the recovery core is a set of pure functions — no clock/storage/random/console/throw-for-control-flow/mutable module state; timestamps passed as ISO strings.
