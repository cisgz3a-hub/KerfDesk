## P1-1 — a relative moveto after Z is parsed as ABSOLUTE, silently misplacing every subsequent contour

`handleMove` decides relative-vs-absolute with `useRel = rel && (k > 0 || state.cur !== null)` ([parse-path-d.ts:242](../../src/io/svg/parse-path-d.ts)). The `state.cur !== null` test is meant to detect "first command of the path" (where the SVG spec says a relative `m` is treated as absolute) — but `handleClose` also sets `state.cur = null` ([parse-path-d.ts:407](../../src/io/svg/parse-path-d.ts)), so **every relative moveto that follows a closepath is also treated as absolute**.

Spec behavior (SVG 1.1 §8.3.2 / §9.3.4, matched by every browser): after `z` the current point is the initial point of the just-closed subpath, and a following `m dx dy` is relative to it.

**Verified repro** (throwaway test, observed output): `parsePathD('M 10 10 L 20 10 Z m 5 5 l 1 0')` starts the second subpath at **(5,5)**; per spec it must start at **(15,15)**. The curve `segments` are built from the same misplaced cursor, so the fairing/export path inherits the identical displacement — the error is self-consistent and therefore invisible to structural checks.

Impact: `z m` sequences are standard output of SVGO's path optimization (relative commands are shorter), so multi-contour icons/fonts/clipart optimized this way import with contours displaced to wrong absolute positions. This is a silent geometry-fidelity failure — the exact class collaboration rule 2 exists for. **No fixture in `src/__fixtures__` contains a `z m` sequence** (grep verified), which is why the perceptual and snapshot suites never caught it, and `parse-path-d.test.ts` has no post-close moveto case.

Fix direction (maintainer's call): track a "first moveto seen" flag instead of inferring firstness from `state.cur === null`; the cursor is already correct after close (`state.cursor = sub.start`), so `useRel` keyed on that flag yields spec behavior. One-line-ish fix + fixture with `z m`.

## P3-2 — coincident-endpoint arcs are dropped by NaN accident, not by design, and a degenerate arc segment survives in curve data

For an arc whose endpoints coincide (`M 10 10 A 5 5 0 0 0 10 10`), `arcToCubics` divides by a zero denominator ([flatten-curves.ts:138-139](../../src/io/svg/flatten-curves.ts): `denominator = 0` when `x1p = y1p = 0`), producing NaN center/angles; `segCount = Math.max(1, Math.ceil(NaN))` is NaN ([flatten-curves.ts:159](../../src/io/svg/flatten-curves.ts)), the `i < NaN` loop runs **zero** times, and the arc contributes no polyline points.

**Verified:** the parse output contains no non-finite points — the outcome coincidentally matches the spec ("if the endpoints are identical, omit the arc"). Two residual concerns:

1. The correctness rests on NaN comparison semantics three calls away from the degenerate math — any refactor of `segCount` (e.g. clamping, `|| 1`) converts the silent omit into NaN geometry.
2. The `curve.segments` array still records an `elliptical-arc` segment to the same point ([parse-path-d.ts:368-380](../../src/io/svg/parse-path-d.ts)); downstream curve consumers (fairing, re-emission) can re-derive the degenerate arc the flattener never validated.

Fix direction: explicit early return in `flattenArc`/`arcToCubics` when `start ≈ end` (spec omit), and skip the segment record like the `rx === 0 || ry === 0` branch already does.

## P3-3 — no test coverage for either behavior

`parse-path-d.test.ts` (215 lines) covers command grammar, arc-flag fusion (H8), non-finite input rejection (S04-001), and the point budget — but has no case for a moveto after closepath (relative or absolute) and no degenerate-arc case. Both P1-1 and P3-2 would have been caught by one short spec-conformance block.

## Verified clean (checked, no finding)

- **Non-finite input coordinates rejected at the boundary** (`finiteNumber`, [parse-path-d.ts:73-79](../../src/io/svg/parse-path-d.ts)) — the S04-001 `1e999` → `XInfinity` G-code hole stays closed.
- **Zero-radius arcs degrade to lines** in both the flattener ([flatten-curves.ts:85-88](../../src/io/svg/flatten-curves.ts)) and the segment record ([parse-path-d.ts:369-370](../../src/io/svg/parse-path-d.ts)) — the old "SVG zero-arc NaN kills import" finding (PR #58 audit, 2026-07-13) is fixed in the current tree.
- **Arc flag grammar** handles fused single-digit flags (`a4 4 0 011 7`), matching SVGO output (H8, [parse-path-d.ts:113-156](../../src/io/svg/parse-path-d.ts)).
- **Point budget** throws at `SVG_IMPORT_LIMITS.points` before memory blowup ([parse-path-d.ts:223-228](../../src/io/svg/parse-path-d.ts)); a malicious-corpus suite exists alongside.
- **Radius-correction, sweep-direction, and quarter-turn splitting** in `arcToCubics` follow W3C F.6.5/F.6.6 faithfully for non-degenerate inputs.
