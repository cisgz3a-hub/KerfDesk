# MCP integration research: 1 October 2026

The initial integration follows the maintainer's request for both standard MCP apps and a separate phone control page. ADR-564 records the permission and machine-execution boundaries.

| Primary source | Verified finding | Implementation consequence |
| --- | --- | --- |
| [OpenAI DevDay 2026 update](https://learn.chatgpt.com/docs/whats-new/devday-2026) | The 29 September announcement includes plugin extensions, MCP Events preview and remote Work access. | It is a recent announcement, but these are distinct capabilities. The initial server does not advertise MCP Events or Work access as implemented. |
| [OpenAI MCP server guide](https://developers.openai.com/plugins/build/mcp-server) | Remote plugins use a public HTTPS MCP endpoint and standard transports. | The first-party Worker exposes a stable Streamable HTTP endpoint, backed by the approved desktop connection. |
| [OpenAI authorization guide](https://developers.openai.com/plugins/build/auth) | OAuth discovery, resource/audience binding and PKCE are required for authorization. | Use the maintained Cloudflare OAuth provider with dedicated storage, rather than a bespoke token server. |
| [OpenAI secure MCP tunnels](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels) | Private tunnels require the relevant OpenAI organization, tunnel and runtime credentials. | Public customer distribution does not assume the maintainer's private tunnel or include an OpenAI API key. |
| [OpenAI developer mode](https://developers.openai.com/api/docs/guides/developer-mode) and [plugin connection](https://developers.openai.com/plugins/deploy/connect-chatgpt) | Private setup, plan/workspace eligibility, public listing and client availability are separate. | Document those limits. Qualifying the HTTP protocol alone does not prove a public ChatGPT listing or every mobile client. |
| [MCP TypeScript SDK](https://github.com/modelcontextprotocol/typescript-sdk) | Current stable v2 server/client packages support the standard protocol. | Pin server/client 2.2.0. Do not force compatibility with the initial OpenAI extension package's legacy v1 peer dependencies. |
| [Cloudflare OAuth provider](https://github.com/cloudflare/workers-oauth-provider) | The maintained provider implements the authorization protocol and token lifecycle. | Pin 1.2.1; verify actual issuer/resource/PKCE and token expiry in the real Worker runtime. Preserve the library's documented retry-compatible refresh behaviour. |
| [Cloudflare Durable Object WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/) | Inbound hibernating WebSockets can coordinate persistent connections without an always-running object. | The PC opens an outbound authenticated WSS connection to its own SQLite Durable Object. No router port forwarding is required. |

Runtime qualification must use the same SDK identity on both sides of `createMcpHandler`: two separately resolved SDK copies fail its class check. The isolated Worker bundles shared MCP source using canonical package aliases. It has its own pinned toolchain and dependency lock; the desktop package does not inherit the Worker's toolchain.

Review tools project only bounded data. They never treat project strings or remote client input as instructions. A matching existing prepared-job owner is required for real review/Frame evidence; the current integration returns unavailable. The desktop remains the live-document authority and all writes retain revision, request-identity, cancellation and Undo checks.

Publication evidence must identify the immutable source, deployed Worker version and actual desktop bundle. Protocol tests, phone-size Chromium rendering, live OAuth, native restart persistence and hardware evidence are separate claims.
