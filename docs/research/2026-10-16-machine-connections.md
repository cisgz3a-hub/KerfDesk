# Desktop machine connections: research and staged delivery

Verified against the linked primary firmware, manufacturer and standards sources on **2026-10-16**. This is a map of the main connection families used by laser cutters, engravers and CNC machines, not certification of every model. Moving upstream branch links are research observations; a delivered adapter needs a recorded firmware/version contract. No physical machine, firmware setting, provider account or network device was operated during this research.

## What the connection needs to describe

The physical link, the wire protocol and the controller are separate choices. Wi-Fi and Ethernet can carry the same IP protocol. USB can expose a serial port, a vendor-specific device, a network card or removable storage. A successful socket or USB connection proves that the endpoint opened; it does not prove that the selected controller understands the job or that motion completed.

Store and display the controller family separately from its supported connection method. Every adapter must define framing, acknowledgement, backpressure, realtime commands, job completion and disconnect behaviour for that family. A generic “Wi-Fi machine” driver cannot supply those contracts.

## Compatibility matrix

“Documented” means the upstream source describes the interface. It does not mean KerfDesk has implemented or physically qualified it.

| Family / interface | Documented connection and execution model | KerfDesk position and next work |
| --- | --- | --- |
| Stock GRBL 1.1 | Serial byte stream, commonly reached through USB; line acknowledgements and separate realtime commands. Sender flow control matters even when the physical connection is fast. [GRBL interface](https://github.com/gnea/grbl/blob/master/doc/markdown/interface.md) | Existing serial driver. Preserve it. A network-to-serial bridge is a separate adapter with its own buffering/reset contract, not stock GRBL network support. |
| FluidNC | USB/serial and Wi-Fi WebUI; configurable enabled Telnet service registers controller channels. Its current WebSocket implementation also has explicit binary/control-message and queue behaviour. [FluidNC overview](https://github.com/bdring/FluidNC), [Telnet server](https://raw.githubusercontent.com/bdring/FluidNC/main/FluidNC/src/WebUI/TelnetServer.cpp), [WebSocket channel](https://raw.githubusercontent.com/bdring/FluidNC/main/FluidNC/src/WebUI/WSChannel.cpp) | Existing desktop Telnet adapter with manually entered target. Retain its explicit channel contract. WebSocket needs a firmware-specific adapter, not a URL substitution. |
| grblHAL | Board/build-dependent wired Ethernet or Wi-Fi. Networking plugin offers raw Telnet, WebSocket, file services and optional discovery; supported services depend on the driver. Raw Telnet passes received payload bytes into the controller stream. [Networking plugin](https://github.com/grblHAL/Plugin_networking), [raw TCP implementation](https://raw.githubusercontent.com/grblHAL/Plugin_networking/master/telnetd.c) | Existing serial driver. Stage 1 adds explicit raw TCP beside FluidNC Telnet. Raw traffic must not undergo Telnet IAC escaping or negotiation. WebSocket/file/discovery support remains separate. |
| Smoothieware | Ethernet command service and file transfer; V1 and V2 differ. V1 documents Telnet, HTTP and Simple File Transfer Protocol. V2 documents a raw shell, FTP and WebSocket command/upload endpoints. The V1 documentation warns against simultaneous web-interface and Telnet access. [Network documentation](https://smoothieware.org/network) | Existing serial driver. Next implement an explicitly selected and pinned network generation, beginning with its command stream; qualify status, cancellation and completion before adding WebSocket or uploads. |
| Marlin | Configured UART or USB-emulated serial. `M28` writes incoming commands to SD until `M29`; optional binary transfer is a separate build feature. [Serial settings](https://marlinfw.org/docs/setting/serial.html), [SD write](https://marlinfw.org/docs/gcode/M028.html) | Existing serial driver. Keep firmware dialect and enabled features explicit. SD transfer is a distinct upload workflow; it cannot be treated as ordinary live streaming. |
| Duet / RepRapFirmware | Manufacturer HTTP API permits third-party clients, sessions, command requests, upload and download; standalone and SBC modes have distinct API definitions. Upload supports a CRC check. [HTTP API](https://github.com/Duet3D/RepRapFirmware/wiki/HTTP-requests), [Duet Software Framework API](https://duet3d.github.io/DuetSoftwareFramework/articles/rest-api.html) | New controller/API family, not a GRBL network target. Start with identity/status and verified file upload, then implement the correct machine/job lifecycle. |
| Host services: OctoPrint / Moonraker | HTTP APIs upload files to a host; the host controls its attached firmware. Moonraker uses HTTP and JSON-RPC, with file transfer restricted to HTTP. Upload can optionally trigger a print. [OctoPrint file API](https://docs.octoprint.org/en/main/api/files.html), [Moonraker file API](https://moonraker.readthedocs.io/en/latest/external_api/file_manager/) | Treat each as a separate host API. Upload must default to no automatic execution. Presence of these services does not establish laser/CNC dialect or physical capability. |
| Ruida DSP | PC USB, Ethernet and USB-stick workflows are documented. OMTech documents `.rd` file transfer and Ethernet/UDP setup for its Ruida-based Polar. [OMTech transfer guide](https://help.omtechlaser.com/hc/en-us/articles/32499286111513-How-can-I-send-laser-files-to-my-laser), [Polar setup](https://omtech.com/blogs/tutorials/setting-up-your-omtech-polar-desktop-engraving-machine) | Existing experimental file export only. Network work requires a Ruida job/protocol implementation with independently accepted fixtures; sending G-code over the current TCP adapter is not a compatible route. |
| Trocen AWC DSP | The manufacturer documents USB communication, USB-disk read/write and network communication for AWC7813/7824. These product pages do not publish a wire protocol. [AWC7813](https://www.sztrocen.com/product-details.php?cid=14&id=18), [AWC7824](https://www.sztrocen.com/product-details.php?cid=14&id=19) | Separate controller/export family. Obtain exact model protocol/SDK and fixture evidence before implementation. Do not infer protocol, ports or support for older AWC models from these pages. |
| TopWisdom DSP | Vendor-authored TL-A1 documentation describes PC USB, USB disk and Wi-Fi setup. The official site could not be fetched; the accessible manual is a third-party mirror. [TL-A1 manufacturer manual, mirrored](https://www.manualslib.com/manual/3135251/Topwisdom-Tl-A1.html), [TL-A1/A3/A4 Wi-Fi instructions, mirrored](https://www.toolots.com/media/attachment/file/T/L/TL-A1_A3_A4%20WIFI%20networking%20instructions_%E5%8A%A0%E6%B0%B4%E5%8D%B0.pdf) | Research lead with an explicit source-host limitation. Obtain current manufacturer documentation and model-specific packet/file contracts. No implementation-ready command protocol was established. |
| Galvo controllers: JCZ LMC / DLC, EZCAD | LMCV4 uses vendor USB; DLC variants include Ethernet. The SDK supplier distinguishes EZCAD2-compatible original LMC V4 Standard from Lite and maps EZCAD3 to compatible DLC hardware. [LMCV4](https://www.ezcad.com/products/lmcv4/), [DLC2 Ethernet](https://www.ezcad.com/products/dlc2-v3/), [SDK compatibility](https://www.ezcad.com/products/ezcad-sdk/) | Dedicated galvo job and device driver work. Verify SDK redistribution terms, OS/architecture, board revision and calibration contract before adopting it. USB here does not establish a serial G-code endpoint. |
| Bluetooth Classic serial / RFCOMM | Bluetooth SPP defines an emulated serial cable between peers. Firmware support remains device-specific; grblHAL lists a Bluetooth plugin with driver requirements. [Bluetooth SPP](https://www.bluetooth.com/specifications/specs/serial-port-profile-1-2/), [grblHAL plugins](https://github.com/grblHAL/plugins) | First qualify an OS-paired serial endpoint where available. The serial adapter still needs a known controller and disconnect/flow-control evidence. Do not advertise all Bluetooth machines as supported. |
| Bluetooth LE / GATT | BLE serial-like services are vendor-specific; they are not Classic SPP. LaserPecker documents USB and its own Bluetooth-dongle workflows. [u-blox BLE serial guide](https://content.u-blox.com/sites/default/files/OBS421-OLS425-BluetoothLowEnergySPA_UserGuide_%28UBX-15012584%29.pdf), [LaserPecker connections](https://support.laserpecker.net/hc/en-us/articles/9542428157071-Connect-Your-Machine-to-LDS) | A BLE adapter needs exact service/characteristic IDs, fragmentation, acknowledgements, authentication and job semantics. A Bluetooth-capable radio alone provides none of those details. |
| xTool and other vendor device APIs | xTool's F1 Ultra/apparel-printer interface page documents BLE discovery/provisioning, USB presented as a virtual network card, LAN discovery and an authenticated WebSocket-TLS service. Older D1/D1 Pro setup uses USB to provision Wi-Fi. [Current interface description](https://support.xtool.com/article/2605), [D1/D1 Pro setup](https://support.xtool.com/article/525) | Model/firmware-specific integration. The documented service architecture does not supply a complete third-party command/authentication SDK. Preserve authentication; do not assume BLE carries jobs, USB is serial, or all xTool models share this contract. |
| Cloud-controlled vendor machines | Glowforge documents Wi-Fi plus internet/cloud connectivity as required for its supported workflow. [Glowforge Wi-Fi requirements](https://support.glowforge.com/hc/en-us/articles/360033633634-Wi-Fi) | Keep artwork export/handoff as the practical baseline. A direct integration needs a supported vendor API and an explicit product/privacy decision; a Wi-Fi radio does not imply a local G-code endpoint. |
| Offline SD / USB storage / panel execution | Marlin exposes SD writes; OMTech supports `.rd` on a USB stick; Haas lists machine memory, removable USB and network files. [Marlin SD](https://marlinfw.org/docs/gcode/M028.html), [OMTech files](https://help.omtechlaser.com/hc/en-us/articles/32499286111513-How-can-I-send-laser-files-to-my-laser), [Haas Device Manager](https://www.haascnc.com/service/online-operator-s-manuals/lathe-operator-s-manual/lathe---device-manager.html) | Preserve file export and explicit operator handoff. Export, transfer, controller selection and execution are distinct events. A copied file is not a connected machine or verified job completion. |
| LinuxCNC / Mach / external motion hardware | LinuxCNC Mesa Ethernet hardware uses a realtime link with dedicated-network requirements. Mach interprets jobs and uses hardware-specific plugins for external USB/Ethernet motion controllers. [LinuxCNC hm2_eth](https://linuxcnc.org/docs/master/html/nb/man/man9/hm2_eth.9.html), [Mach4 manual](https://www.machsupport.com/wp-content/uploads/2014/05/Mach4%20Scripting%20Manual.pdf) | Prefer compatible job export or a defined host integration. Do not send GRBL commands directly to a Mesa/Mach motion card or attempt realtime step generation from Electron. |
| Legacy/industrial serial and field buses | Haas' older mill documentation includes RS-232 DNC. LinuxCNC documents buses including Ethernet, EtherCAT and Modbus. These can serve different layers of a machine. [Haas 2009 mill manual](https://www.haascnc.com/content/dam/haascnc/en/service/manual/operator/english---mill-operator%27s-manual---2009.pdf), [LinuxCNC architecture](https://linuxcnc.org/docs/master/html/en/getting-started/about-linuxcnc.html) | Scope each exact controller. RS-232 DNC needs its own framing, flow control and postprocessor; RS-485/Modbus, CAN or EtherCAT peripheral links are not automatically desktop job interfaces. |

## Delivery sequence

1. **Broad connection foundation, implemented locally on 2026-10-16.** The established USB serial path remains available. Desktop network controls retain FluidNC Telnet and add grblHAL raw TCP, with the selected protocol owning setup, handshake and Retry. User-entered host and enabled port avoid speculative discovery. Connection loss closes the owned session; uncertain writes are not retried or replayed. See [the implementation and verification record](../implementation/2026-10-16-machine-connections.md) for evidence and limits. Installed-package and physical-machine qualification remain separate.
2. **Additional documented network command channels.** Add a pinned Smoothieware generation, then firmware-specific WebSocket channels for FluidNC/grblHAL/Smoothieware where useful. Confirm binary versus text frames, subprotocol/path, realtime-byte treatment, buffer limits and session ownership. Smoothieware V1/V2 must not be silently interchangeable. Expose only implemented combinations in the connection UI.
3. **Controller storage and host uploads.** Add upload-only workflows for documented firmware/host APIs, with bounded filenames, transfer completion and independent content checks where supported. Separate upload from Start. Add execution only when controller-selected content can be matched to the exact reviewed artifact and the canonical machine lifecycle. Preserve the existing offline export route throughout.
4. **Proprietary DSP and native USB/galvo families.** Work one controller family at a time, beginning with an independently accepted output fixture and a documented protocol/SDK. For Ruida, qualify the existing file output before claiming live USB/UDP support. Trocen, TopWisdom and JCZ require separate adapters; a shared cable is not evidence of a shared command set.
5. **Bluetooth and vendor integrations.** Qualify paired SPP endpoints first, then a specifically documented BLE device or vendor API. Vendor authentication, device IDs and credentials remain scoped to that adapter. Add discovery only as an explicit bounded operation with evidence of the advertised service, not automatic commands sent across the LAN.
6. **Host-controlled and industrial systems.** Add matching exports or documented LinuxCNC/Mach/industrial-host bridges when a real target model and supported API are available. Retain realtime motion inside the controller/host designed to perform it.

This sequence is an engineering recommendation based on the existing code and documented interfaces. It is not a promise that every listed family is already supported or an instruction to buy hardware.

## Acceptance evidence for each implemented adapter

- Record exact controller, firmware version/build, configured service and wire framing. Distinguish declared capability from observed session identity.
- Use loopback/mock endpoints to test fragmented reads, bounded buffers, acknowledgement ownership, ordered writes, timeouts, duplicate requests, wrong protocol, network loss and manual reopen. Preserve raw realtime bytes where that controller specifies them.
- Exercise setup, handshake, Retry, disconnect and session replacement through the desktop UI. A native bridge test alone does not prove that the operator can select and use the connection correctly.
- Keep Frame and Start on their canonical paths. A completed Frame for unchanged footprint/placement remains the ordinary Start policy gate; each Start claims the exact reviewed current program. Connection changes cannot restore old coordinate evidence. Findings belong in Job Review, with no new licence/account/network-quality policy gate.
- For uploads, distinguish bytes transferred, artifact accepted, job selected, job started and physical completion. Never infer the last four solely from an HTTP success or socket write.
- Record installed-desktop, real-controller, air-cut and material results separately. This research and loopback tests establish none of those physical qualifications. Hardware operation needs the user's explicit request.

## Material gaps and source limits

The existing [machine protocol workflow record](../implementation/2026-10-07-machine-protocol-workflows.md) establishes the prior serial/FluidNC Telnet baseline and experimental Ruida file-only boundary; the new raw TCP work needs its own verification record. No public protocol sufficient for a complete Trocen, TopWisdom, LaserPecker, xTool or Glowforge third-party driver was established in this pass. That is a research limit, not a claim that such documentation cannot exist.

The FluidNC wiki and the Ruida/TopWisdom manufacturer homepages could not be fetched with the research browser. FluidNC claims above instead use its own repository; Ruida uses machine-manufacturer instructions; TopWisdom's manufacturer-authored mirrored material is explicitly qualified. SDK marketing establishes an integration route, not redistribution rights or controller acceptance.

Upstream firmware source was used to understand interfaces. No external implementation was copied or added as a dependency. KerfDesk remains proprietary; any future SDK, native library or bundled asset must pass the repository's licence and third-party notice requirements.
