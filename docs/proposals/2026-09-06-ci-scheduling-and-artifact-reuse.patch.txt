+## ADR-235 - Parallel full-suite CI and exact-revision deploy artifacts
+
+**Date:** 2026-07-19
+**Status:** Accepted (maintainer request to make GitHub CI and deployment faster)
+
+### Context
+
+Core CI ran `release:check` as one serial job. A measured main run spent about 18 of its 21 minutes
+in 1,056 Vitest files because the two-vCPU runner intentionally uses one Vitest worker to prevent
+orchestrator starvation. After that run passed, the Cloudflare workflow checked out the same SHA
+and repeated the full gate for another 21 minutes even though the Pages upload took seconds.
+Dependency caching was already active and installation took about ten seconds, so caching could not
+materially reduce the critical path.
+
+### Decision
+
+1. Keep `release:check` as the serial local, manual-deploy, and desktop-release authority. Core
+   GitHub CI preserves the same checks collectively, but divides them into parallel static/policy,
+   web-build, Electron-build, and unit-test lanes.
+2. Run Vitest as four file shards on four GitHub runners. Each runner retains the existing CI limit
+   of one Vitest worker, so sharding reduces wall time without reintroducing the worker-RPC
+   starvation that the limit prevents. An aggregate job with the established CI check name fails
+   unless every lane and every shard succeeds.
+3. Build the web bundle from full Git history so its revision count and SHA remain correct, then
+   upload `dist/web` as a seven-day artifact named for that exact workflow SHA. Documentation-only
+   changes skip core CI and browser smoke; source, configuration, and workflow changes retain the
+   complete gates.
+4. A normal main deployment may run only after that exact CI workflow succeeds. It checks out the
+   triggering SHA and downloads the web artifact from the triggering workflow run with read-only
+   Actions permission. Missing artifacts, digest mismatch, or a missing `index.html` fail before
+   Cloudflare publication. The deploy never substitutes a bundle from another SHA or run.
+5. A manually dispatched deploy has no originating CI artifact, so it retains the full
+   `release:check` rebuild before publication. ADR-158 remains unchanged: browser smoke is visible
+   and independent, not an additional production-deploy dependency.
+
+### Consequences
+
+- Code changes still exercise every unit, property, snapshot, type, lint, license, dependency,
+  build, and policy check; the optimization changes scheduling rather than coverage.
+- The expected core-CI critical path falls from about 21 minutes to roughly 5-7 minutes, and normal
+  commit-to-production time no longer includes a second 21-minute verification pass.
+- Four test runners and separate build/quality runners use more concurrent capacity and modestly
+  more setup minutes. Cancellation still retires obsolete branch runs when a newer commit lands.
+- The CI-produced web bundle becomes the deployment input, removing the previous build-after-check
+  time-of-check/time-of-use gap while retaining an exact-SHA checkout for repository provenance.
